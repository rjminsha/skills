# Step 3 — Coordinator: Review and Merge

Once **all** sub-agents from Step 2 have completed, the coordinator agent reads every `temp/[repo]-analysis.md` and `temp/[repo]-domain.md` file (not `temp/refresh-log.md`, which is only used for the refresh caveat below and in Step 5) and produces four top-level output files.

---

## Output files

### `DOMAIN-LANGUAGE.md`

A glossary of key domain terms used in or across repositories. Its purpose is to establish shared language for user-stories and feature discussions — it captures *business and domain vocabulary*, not implementation jargon.

Merge rules:
- Identical terms → keep one definition; note if repos differ.
- Conflicting definitions → choose the most precise; add a note `(varies: see [repo])`.
- Repo-specific terms that are not meaningful org-wide → still include, tagged `[repo-name]`.

**Critical check before writing** — sub-agents over-include, so re-apply the Step 2 include/exclude test to every merged term. Drop any term that is developer process or tooling (PR gates, commit conventions, CI/CD pipeline types, implementation-tracking artefacts, script resume files, session timeouts) or that is a standard engineering/vendor term needing no project-specific explanation. Keep definitions to one or two sentences. A small, sharp glossary is better than a complete one.

**Format:**

```markdown
# Domain Language

> Canonical terms used across this repository / organisation.
> Last updated: YYYY-MM-DD

| Term | Definition | Repos |
|---|---|---|
| TermName | Plain-English definition. | all / [repo-name] |
```

### `MAP.md`

A table-of-contents and structural index. Its purpose is to give a quick-reference view of where things live across the codebase(s), enabling progressive disclosure for agents and humans alike.

For a **single repo**, omit the `## Repositories` table and the `Repository` column from the waypoints table — they add noise when there's nothing to disambiguate. If the repo is a fork, keep one line under the header: `> Fork of https://github.com/owner/upstream-repo`.

For **multiple repos**, order the `## Repositories` table per [Fork handling](#fork-handling) (below, after `SUMMARY.md`): non-forks first, then forks grouped by upstream. The `Waypoints` table follows the same repository order.

**Format (organisation — multiple repos):**

```markdown
# Map

> Structural index of this repository / organisation.
> Last updated: YYYY-MM-DD

## Repositories

| Repository | Fork of | Type | Purpose (one line) | Primary language |
|---|---|---|---|---|
| [repo-name](./repo-name/) | — | code | … | Go |
| [fork-name](./fork-name/) | https://github.com/owner/upstream-repo | code | … | Go |

## Waypoints

| Repository | Path | Purpose |
|---|---|---|
| repo-name | `src/` | Application source |
| repo-name | `helm/` | Deployment chart |
```

**Format (single repo):**

```markdown
# Map

> Structural index of this repository.
> Last updated: YYYY-MM-DD

## Waypoints

| Path | Purpose |
|---|---|
| `src/` | Application source |
| `helm/` | Deployment chart |
```

### `SUMMARY.md`

A high-level summary covering purpose, status, activity, language, frameworks, configuration, secrets, type, deployment, and license. Organised with a ToC, a summary index table, and per-repository sections. Its purpose is to give a new team member or agent enough context to orient themselves without reading source code.

**Ordering**: non-fork repositories first, sorted by status group then alphabetically within each group. Status group order: `very-active` → `active` → `stable` → `experimental` → `new` → `stale` → `archived`. Forks follow, grouped by upstream (see [Fork handling](#fork-handling)). Apply this order consistently to the `## Repository index` table (including its `### Forked repositories` subsection) and to the `## Repository details` sections.

**Refresh caveats**: if any repo's refresh outcome (from its analysis file) is `skipped`, `fetched only`, or `failed`, add a line under the Overview: `> Not fully refreshed: repo-a (skipped: uncommitted changes), repo-b (failed: offline). Findings for these may be out of date.` Omit the line if every repo was refreshed or already current.

**Format (organisation — multiple repos):**

```markdown
# Summary

> Generated by understand-repos on YYYY-MM-DD.

## Table of contents
- [Overview](#overview)
- [Repository index](#repository-index)
- [Repository details](#repository-details)

## Overview
[Two–four sentences about the purpose and scope of the organisation.]

| Repository | URL | Fork of | Type | Status | Language | Deployment | License |

### Forked repositories

## Repository details
```

### `DETAILS.md`

A per-repository deep-dive. Sorted alphabetically by repository name. Its purpose is to give enough detail to understand what a repository does and how to work with it, without reading source code.

**Treatment by status:**
- `very-active`, `active`, `stable`, `new`, `experimental` → full entry (all sections below). For `new` repos with little content, keep sections short rather than padding.
- `stale`, `archived` → light entry: URL and Purpose only — omit Key directories, How the pieces fit together, and FAQ.

**FAQ section**: do not generate FAQ questions from scratch. After Step 4 completes, copy the verified Q&A pairs from the self-quiz into the FAQ section for each repository. Only include questions that passed (correct or partial) — omit questions marked incorrect or unanswered. This guarantees the FAQ is accurate.

**Format:**

```markdown
# Details

> Per-repository deep-dive. Sorted alphabetically.
> Last updated: YYYY-MM-DD

---

## repo-name

**URL:** https://github.com/org/repo-name
**Fork of:** https://github.com/owner/upstream-repo   <!-- forks only; "unknown" if undetermined; omit otherwise -->
**Status:** very-active

### What it does

[Expanded from Purpose — concrete specifics about what this repository does.]

### Key directories

| Path | Purpose | Notable files |
|---|---|---|
| `src/` | Application source | `main.go` (entry point), `config.go` (config loading) |
| `helm/` | Deployment chart | `values.yaml` (default config) |

### How the pieces fit together

[2–4 sentences: how major components relate, data flow, CLI/API surface.]

### FAQ

**How do I run this locally?**
[Answer.]

**How do I deploy it?**
[Answer.]

**Where does configuration come from?**
[Answer.]

**Where are secrets managed?**
[Answer.]

[Additional verified Q&A pairs from Step 4 self-quiz, repo-specific.]
```

**Light entry format (stale / archived):**

```markdown
## repo-name

**URL:** https://github.com/org/repo-name
**Fork of:** https://github.com/owner/upstream-repo   <!-- forks only -->
**Status:** stale | archived

[Purpose sentence(s). No further sections.]
```

## Fork handling

Applies to `SUMMARY.md`, `MAP.md`, and `DETAILS.md`. Use each repo's `## Fork` section from its Step 2 analysis file.

- **Source is always visible**: every repository that is a fork shows its upstream URL (`Fork of`) wherever its own URL is shown. If fork status is `unknown`, show `unknown` rather than leaving it blank.
- **Non-forks first**: original (non-fork) repositories come first, ordered by status as described under `SUMMARY.md`; the forked-repositories groups follow.
- **Group by upstream**: forks of the same upstream sit together under one heading for that upstream, regardless of their individual status. Within a group, sort by status group then alphabetically. Groups themselves are sorted alphabetically by upstream.
- **`DETAILS.md`** stays alphabetical by repo name (it is a lookup file), but each fork entry carries a `**Fork of:**` line.
